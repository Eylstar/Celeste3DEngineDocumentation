ExportGenerator

Class Static
You don't need to call this class yourself. It runs automatically the first time an OBJ model loads, and exists mostly to explain what the .export.dat files sitting next to your OBJ assets actually are.

When a MeshRenderer loads a model in the OBJ format, the Engine doesn't parse the raw .obj text file every single time. It's very inefficient and takes a long time to load. The first time a given model is loaded, it parses it once, and with the result writes out an .export.dat file that's going to be placed in your EnginePaths.CustomExportsPath folder (if the path was set, if not it returns).

The Export file is automatically named exactly like the OBJ one, so when you call to load the obj model with a string, the engine first finds the export file already there and reads it instead, the original .obj file isn't touched again.

Why use Export format

An OBJ file is plain text, and reading it means splitting lines, parsing floating numbers, resolving vertex, texture coordinate and normal indices, fanning arbitrary polygon faces into triangles, and computing normals from scratch if the file doesn't provide any. None of that is expensive once, but it adds up if it happens on every single load and on every single OBJ model.

.export.dat skips all of it. It's a small binary file, an integer vertex count followed the vertices position, texture coordinate and normal. Everything the OBJ parser would normally compute has already been done once and baked directly into the file. Loading it is just reading a result, nothing to resolve.

Also, because the names are exactly the same, and the OBJ loading is technically a fallback of the export loading, you can and should ship your mod with only the export files, since they are significantly smaller in disk size.

Keeping Exports in Sync

The Engine only checks whether a .export.dat file exists for a given model name, it never compares it against the source .obj file in any way. If you update or replace an OBJ file after its export was already generated, the Engine keeps loading the old export and ignores your changes. Delete the matching .export.dat file yourself whenever you update the source OBJ, so a fresh one gets generated from the new version on the next load.

Prefer GLB

This whole export pipeline exists mainly to make the OBJ path usable at all, it's not the Engine's primary format. GLB and GLB models don't need any of this and they support things OBJ never will here, skinning and animation among them. Unless you need for example to switch an object textures at runtime with an external png (like the Skybox) prefer using GLB.

ConvertObjToExport() can only write files for mods that aren't packaged as a zip, it needs to write a real file next to your assets on disk, which isn't possible from inside an archive. Because a shipped mod is zipped, the automatic export step won't run for your players at all, every OBJ load will parse the raw file. Generate and include the .export.dat files yourself as part of the mod, and don't ship the OBJ files, this will also save a lot of space.
