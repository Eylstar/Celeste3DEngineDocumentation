EngineCallbacks

Class Static

EngineCallbacks exists to solve one specific problem. Making sure your setup code still runs after a Save and Quit, in cases where you want to mix the Celeste Gameplay and the Engine 3D rendering (for 3D backgrounds for exemple). The EngineEntity being a Lonn Entity, is only placed in a specific room in Lonn. The Entity is persistent, so it follows you through rooms. EngineEntity gets rebuilt following a save and quit, even though the normal way you'd hook into engine loading, EngineEntity.OnEngineLoad, doesn't survive that. This page explains the whole mechanism it's part of, not just the class itself, because none of it makes sense in isolation.

Why OnEngineLoad Isn't Enough

When your EngineEntity is marked persistent, Celeste keeps the same live object alive as the player moves between rooms, it's the standard Everest persistence tag, and it works exactly as expected within a single play session.

A save and quit, or even relaunching Celeste, is a different situation entirely. The whole game process ends, every static field resets, every event subscription is gone with it. Whatever subscribed to OnEngineLoad in the first place usually does it from the constructor of a custom Entity you placed in Lönn, something like this:

The usual place OnEngineLoad gets subscribed 
public MySceneBuilder(EntityData data, Vector2 offset) : base(data.Position + offset)
{
    EngineEntity.OnEngineLoad += StartBuildingScene;
}

That constructor only runs when Celeste loads the specific room this Entity was placed in. This is where the room your persistent Engine gets rebuilt in and the room your subscribing Entity lives in can quietly become two different things. The Engine, being persistent, follows the player from room to room in memory, so by the time a save and quit happens, the room recorded to respawn it in is simply wherever the player happened to be standing, not necessarily the room your Entity was placed in. Walking back into that recorded room respawns the Engine correctly, but it doesn't walk you back through your Entity's own room, so its constructor, and the subscription inside it, never runs again. The Engine can rebuild itself because it has that logic built in, your Entity has no equivalent, nothing tells Celeste to place it again outside of normally loading the room it lives in.

EngineCallbacks exists specifically to give that respawned engine a direct way to call back into your mod, without depending on your Entity, or anything else, being placed again first.

How the Respawn Actually Happens

Whenever your persistent EngineEntity is removed, leaving the room it lives in while persistent, the Engine records the current map, which room you left from, your model, texture, export, font and audio paths, and marks that map as needing a respawn, into save data that actually survives a save and quit, unlike anything in memory.

From then on, every time any level loads anywhere in the game, the Engine checks whether the current room matches a room it's waiting to respawn something in. If it does, and no EngineEntity already exists there, it builds a brand new one directly in code, using the saved paths, and adds it to the level itself.

This only fires for the exact room you left from, not just the same map. Leaving from room B and later walking into room C on the same map won't trigger anything, only walking back into room B will.

Registering and Arming a Callback

Using EngineCallbacks is two separate steps, and mixing them up is the easiest way to end up confused about why it isn't working.

RegisterCallback(id, callback) maps a string ID to an actual function. This has to happen unconditionally, every single time your mod loads, regardless of which room the player is currently in or whether a respawn is even needed this session. The natural place for it is your own EverestModule.Load(), which always runs once when the mod loads, completely independent of rooms or saves.

CreateCallbackID(scene, id) is the other half, and it's what actually arms the respawn for a specific map. Call it whenever your engine setup finishes, both the first time it loads normally through OnEngineLoad, and again inside whatever function you registered as a callback. It tells that map's save data which ID to invoke if this engine ever needs to be rebuilt later.

The ID and the function it points to are kept alive by two completely different mechanisms, which is why this survives a full game close. The ID itself is written into your save file through Celeste3DEngineModuleSaveData, real persistence, it's still there after quitting Celeste entirely. The function it maps to is never saved anywhere, it doesn't need to be, RegisterCallback() rebuilds that mapping identically every time your mod loads, which happens automatically on every game launch, before any level or save file is even touched. The two only need to agree on the same ID when they meet again.
The armed flag is consumed the moment a callback actually fires, it doesn't rearm itself. If you want your setup to keep working across more than one save and quit and respawn cycle on the same map, call CreateCallbackID() again inside the callback itself, not just in your original OnEngineLoad handler.

In practice, your EverestModule and whatever builds your 3D scene are usually two different classes, your scene builder is often a custom Entity placed in Lönn, subscribing to OnEngineLoad from its own constructor. RegisterCallback() runs from Load(), at game boot, before any room has ever loaded, so there's no instance of that Entity to call a method on yet, nothing has placed one in a Scene. The function you register has to be reachable without an instance, a static method on your builder class, that Load() can reference directly by name.

Wiring up a persistent Engine across two classes 
//Your EverestModule, boots once per session, before any room loads
public class MyMod : EverestModule
{
    public override void Load()
    {
        //A static method reference, no instance of MySceneBuilder exists yet
        EngineCallbacks.RegisterCallback("MyMod.MainScene", MySceneBuilder.OnRespawn);
    }
}

//Your scene builder, normally placed in Lönn, a separate class entirely
[CustomEntity("mymod/sceneBuilder")]
public class MySceneBuilder : Entity
{
    public MySceneBuilder(EntityData data, Vector2 offset) : base(data.Position + offset)
    {
        //The normal path, the first time this room loads through Lönn
        EngineEntity.OnEngineLoad += BuildScene;
    }

    //The respawn path, called directly by EnsureEngine, no Entity involved at all
    public static void OnRespawn(EngineEntity engine, Level level)
    {
        BuildScene(engine, level);
    }

    static void BuildScene(EngineEntity engine, Scene scene)
    {
        Scene3D myScene = new Scene3D();
        // ...build your scene here...
        EngineEntity.LoadScene(myScene);

        //Arm it again for the next possible respawn
        EngineCallbacks.CreateCallbackID(scene, "MyMod.MainScene");
    }
}
If you have more than one map using this pattern, or more than one distinct setup routine, use a different, stable ID for each. Registration is a single global dictionary shared by the whole mod, not scoped per map, the map specific part lives entirely in what CreateCallbackID() saves.

Methods

Method Return type Description
RegisterCallback(string id, Action<EngineEntity, Level> callback) static void Maps a callback ID to a function, call this unconditionally every time your mod loads
CreateCallbackID(Scene scene, string id) static void Arms the given callback ID to be invoked if this map's Engine needs to respawn later
